## 1. Project Overview

`master-backend` is a REST API backend for an internal enterprise management system, apparently for a construction company (the document-sharing email template hardcodes "Pooja Construction" — **(inferred)** company identity). It is a **modular monolith** that unifies five business domains behind one Express server and one PostgreSQL database:

- **Store / Procurement** — multi-stage purchase-indent → vendor bidding → PO → goods-receipt → payment workflow, plus inventory and a generic dynamic CRUD layer over almost the entire schema.
- **HR (HRFMS)** — recruitment, onboarding, attendance, leave, gate passes, salary advances/loans, payroll, project deployment, exit/offboarding, and letter generation.
- **Checklist / Delegation** — recurring compliance checklists and one-off delegated tasks with a calendar-aware scheduling engine.
- **Petty Cash** — cash float credits, expense claims/approvals, and a per-person running ledger.
- **Document Sub-Manager** — company document, subscription, and loan lifecycle/renewal tracking with email-based sharing.

**Target clients**: an internal single-page frontend (`master-frontend`, a sibling project in this monorepo) consumed by company staff/admins — not a public/third-party API. CORS reflects any origin with credentials, consistent with a single trusted internal frontend rather than a multi-tenant public API.

## 3. Architecture

**Pattern**: modular monolith — each business domain lives under `src/modules/<name>/` with its own `controllers/`, `routes/`, and (inconsistently) `services/`, `repositories/`, `validators/`, `types/`. This is **not** a strict layered architecture: layering discipline varies significantly by module (see below), and one controller (`generic.controller.ts` in the store module) acts as a schema-agnostic CRUD layer that bypasses per-module boundaries entirely.

**Request lifecycle** (typical case):

```
server.ts → app.ts middleware chain → routes/index.ts (mounts /api/<module>)
  → module router → [requireRole / scopeToFirmAccess]* → [validate(zodSchema)]*
  → controller → [service →] [repository →] Prisma Client → PostgreSQL
  → asyncHandler catches rejection → error.middleware.ts → JSON error response
```
(*optional — only applied in the `checklist` and `hr` modules; `store` and large parts of `document`/`petty-cash` have no role gating.)

**Layering by module** (from richest to thinnest):
- **store**: has `repositories/` for the indent workflow, but the `generic.controller.ts` entity endpoint queries Prisma directly with no repository/service abstraction at all, and duplicates indent business logic separately from `IndentService`.
- **document / petty-cash**: consistent controller → service → repository → Prisma layering.
- **checklist**: controller → service (calendar engine, delay calc) → Prisma directly (no repository layer).
- **hr**: controllers call Prisma directly in most sub-features (no repository layer); a couple of standalone `services/` exist (audit log, notification stub). One sub-feature (`indent` — recruitment requisitions) is backed by a flat JSON file (`src/modules/hr/data/hr_indents.json`), not Postgres at all.

**Cross-cutting middleware** (`src/middleware/`): JWT auth, Zod validation, global error handling. Role/firm-scoping middleware (`requireRole`, `scopeToFirmAccess`) physically lives under `src/modules/checklist/middleware/` but is imported and reused by the `hr` module too — a cross-module dependency worth knowing about if that folder is ever moved.

## 7. Core Business Logic

**Store — Indent workflow** (`Indent` model, one wide row per line item):
- Stages gate on `actualN`/`plannedN` field pairs (1 through 5) plus a final store-out approval; each stage transition computes a `time_delayN` and derives the next `plannedN` (e.g. `planned2 = skipSunday(actual1)`).
- Rejecting at stage 1 (`vendor_type==='Reject'`) cascades null-outs of every downstream field, dead-ending the record.
- **This workflow is implemented twice**, once in `IndentService`/`IndentRepository` (for the dedicated `/indents/...` endpoints) and again inline inside `GenericController` (for direct `/entity/indent` PATCHes) — the two paths already diverge on vendor-field shape and are not guaranteed to stay in sync.
- Stage-reset endpoints always reset the target stage *and everything after it*, never a downstream-only reset, and re-trigger `pc_report` KPI recalculation.

**Store — generic entity engine**: resolves any `snake_case` URL table to its Prisma camelCase model via DMMF introspection, casts field types automatically (BigInt/Int/Float/Boolean/DateTime/String), applies a hardcoded `TABLE_INCLUDES` relation map for eager loading, and layers query-param filtering (`gte__`, `ilike__`, `not_null__`, etc.), pagination (offset or cursor), and an LRU response cache with per-table TTLs and dependency-based invalidation (e.g. writing `indent` also purges `inventory`/`pc_report` caches).

**Checklist — calendar exclusion**: a date is excluded from scheduling if it's a `Holiday`, not present in the `WorkingDayCalendar` allow-list, or matches the doer's personal `User.day_off`. Recurring occurrences are generated over a rolling 1-year horizon; each candidate date is nudged forward (day-by-day, bounded iteration) until non-excluded. Nth-weekday-of-month frequencies (including a permanent typo, `end-of-4rth-week`) skip a month entirely if that weekday-occurrence doesn't exist.

**Checklist — recurrence "groups"**: a group is a fingerprint of `(firm_id, doer_id, task_description, frequency)`, not a real foreign key — editing the description on one occurrence silently detaches it from its siblings.

**Checklist — delegation extension**: submitting with `status:'extend'` requires a `next_extend_date` and logs a `DelegationDone` row without resolving the task; approval reschedules the task to that date and resets status to `pending`. No cap on how many times a task can be extended.

**Petty Cash**: credits are auto-approved; expenses start `PENDING` and require an explicit approve/reject. Ledger entries are only written on credit creation and expense *approval* (never on submission/rejection). Balance is a running total computed from the person's last ledger row — vulnerable to backdated/out-of-order inserts. Credits and expenses share one global serial counter (different prefixes, same sequence) — expect gaps.

**Document module**: renewals snapshot the prior state into an append-only `DocRenewal`/`DocSubscriptionRenewal` row before overwriting the parent. Subscription status walks `"" → Approved/Rejected → Paid"` (payment only allowed from `Approved`). Loan closure is strictly sequential: foreclosure → documents collected → NOC collected → settlement, each step gated by a string-status check on the previous.

**HR — advance/loan**: an advance auto-computes `noOfMonths` from amount/monthly-deduction if omitted; approving without an existing `loan_id` always creates a **new** `HrEmployeeLoan` — nothing prevents two concurrent active loans per employee, yet payroll only reads `loans[0]`, so a second loan is silently ignored during payslip deduction.

**HR — exit workflow**: blocks marking an employee `left`/`completed` while they have an outstanding loan, *unless* the request body claims `advancePaymentSettled: true` — this is trusted client input and is not cross-checked against the loan's real balance, so the block is bypassable.

**HR — leave approval**: on approval, can reassign affected `ChecklistTask`/`DelegationTask` rows to another doer (per submitted `taskDecisions[]`), and day-by-day upserts `HrAttendance` rows to `status:'leave'` for the whole leave range.

**HR — payroll**: computed independently in two places (`getPayroll`, `generatePayslip`) from attendance counts and a hardcoded 9-hour day / 12% PF / 0.75% ESIC — **the configurable `HrSalaryStructure` percentages are stored but never actually consulted by payroll math**, a real gap between the "salary structure" feature and what payslips compute.

**Cross-cutting role/scope model** (`checklist` + `hr` modules only): `SUPER_ADMIN` unrestricted; `ADMIN` scoped to `req.user.permittedFirms`; `USER` scoped to only their own records (`doer_id`/`employee_id` match). An `ADMIN` with an empty `permittedFirms` array is deliberately scoped to a sentinel `firm_id:-1` (zero results) rather than falling open.

## 10. Conventions & Patterns

- **Naming**: two eras coexist — legacy `snake_case`/`created_at` (Store, Checklist, HR core tables) vs newer `camelCase`/`createdAt` (Petty Cash, Doc Sub-Manager). Match whichever era the file you're editing already uses; don't mix within one model.
- **Route aliasing**: many modules mount the same router under two base paths for frontend back-compat (`/hr` & `/hrfms`, `/document` & `/doc-submanager`, petty-cash also aliased at bare `/api/*`). If you add a route, check whether it needs mirroring under the alias too.
- **Error handling**: throw `ApiError.badRequest(...)`/`.notFound(...)`/etc. (or `new ApiError(status, message, errors?)`) inside controllers/services; wrap async route handlers in `asyncHandler(...)` so rejections reach `next()`; never `console.error` and swallow — let the global `error.middleware.ts` produce the JSON error shape `{success:false, statusCode, message, errors?, stack?(dev only)}`.
- **Validation**: Zod schemas + `validate.middleware.ts` for `{body,query,params}` — but coverage is inconsistent; many `PATCH`/update endpoints across store/hr/checklist accept raw untyped `req.body`. When adding a new mutating endpoint, add a Zod schema even if a neighboring endpoint didn't.
- **Logging**: `morgan('dev')` for HTTP access logs; ad hoc `console.log`/`console.warn`/`console.error` (some with emoji prefixes) elsewhere. No structured/correlated logger — don't assume log aggregation beyond stdout.
- **Auth pattern**: `authenticateJWT` reads only the `Authorization: Bearer <token>` header (cookie-parser is registered but not used for auth). **In non-production environments, a missing header silently authenticates as a fake `SUPER_ADMIN`** — be aware this can mask missing-auth bugs in dev/staging.
- **Testing**: none exists. If asked to add tests, there's no existing harness/convention to follow — you're establishing one from scratch (confirm test runner choice with the user first).
- **Generic CRUD escape hatch**: before adding a new bespoke CRUD endpoint for a simple table, check whether `/api/store/entity/:table` already covers it — but see the security caveat in §11 before recommending its use for anything sensitive.

## 11. Known Gotchas / TODOs

Flagged from code inspection — treat these as **"don't touch without reading the surrounding code first"** or **"raise with the user before changing behavior that depends on this."**

**Security-sensitive:**
- **`/api/store/*` has no auth middleware at all** — unlike every sibling module, the store router is mounted with no `authenticateJWT`, exposing user CRUD, login, the entire indent workflow, stage resets, file access, and the generic entity CRUD with no token required.
- **Store login compares plaintext passwords** (`UserController.authenticate` — no bcrypt/argon2 despite `bcrypt` being a listed dependency).
- **The generic `/api/store/entity/:table` endpoint is an unrestricted CRUD surface over the entire Prisma schema** — any reachable model (including HR salary/payslip/employee data) can be created/read/updated/deleted by table name, with no per-table allowlist or field-level authorization.
- **Dev-mode auth bypass**: `auth.middleware.ts` fabricates a `SUPER_ADMIN` session when no `Authorization` header is present and `NODE_ENV !== 'production'` — a foot-gun if any non-prod environment is treated as trustworthy.
- **CORS is `origin: true`** (reflects any request origin) with `credentials: true` — effectively open CORS; confirm this is intentional before hardening.
- Several modules (document, petty-cash) apply JWT auth but **no role/ownership checks** — any authenticated user can approve expenses, settle loans, or modify any document/subscription regardless of role.
- HR's recruitment-indent sub-feature has no role check either, and is the one sub-feature backed by a flat JSON file (`hr_indents.json`) instead of Postgres — no transactional safety under concurrent writes.

**Data-integrity / schema:**
- **Migration drift**: Petty Cash, Doc Sub-Manager, and most of HR exist in `schema.prisma` with no corresponding `prisma/migrations/*` folder — they were pushed out-of-band. Running `prisma migrate dev` cold in a fresh environment may not reproduce the current production schema; reconcile this before treating migrations as the source of truth.
- **Duplicated indent-workflow logic** between `IndentService` and `GenericController` — a fix applied to one code path (e.g. a new stage-transition rule) must be mirrored in the other or they will silently diverge.
- **Non-atomic sequence generation** (`SequenceService.generateIndentNumber`, etc.) computes `MAX()+1` outside a row lock — concurrent requests can theoretically produce duplicate human-readable indent/issue numbers.
- **Hardcoded fiscal year** in `SequenceService.generatePoNumber` (`STORE-PO-25-26-...`) — needs a manual code change every fiscal year.
- Ledger balances (petty cash) and payroll loan deduction (HR) both assume strictly ordered, single-active-record invariants that are not enforced at the DB level (no unique constraint on "one active loan per employee"; no reconciliation job for out-of-order ledger inserts).

**Placeholder / dead code:**
- HR `DashboardController.stats` returns **hardcoded fake data** for `upcomingBirthdays` and `openIndents` mixed in with real computed fields.
- `src/modules/store/routes/indent.routes.ts` is defined but never mounted — dead file.
- `dashboard.validator.ts` in HR is defined but never referenced by any route.
- `PettyCashLedgerType.DEBIT` enum value is defined but never used in code.
- HR's global unmatched-route handler returns `200 {success:true,data:[]}` instead of a 404 — a typo'd or unimplemented endpoint looks like a successful empty response to the frontend rather than an error.

**Documentation debt:**
- The pre-existing `README.md` and `BACKEND_WORKING_STRUCTURE.md` at the repo root **only describe the Store module** and predate HR, Checklist, Petty Cash, and Document — do not trust them for anything outside Store without cross-checking current code (this file supersedes them for those domains).
- Checklist module business rules reference an external "reference/architecture doc" (`checklist_delegation_architecture.md`, one directory up from `master-backend`) for the calendar-exclusion and delay-calculation rules — consult it for full rationale if extending that engine.
